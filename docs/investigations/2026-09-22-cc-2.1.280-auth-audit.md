# Claude Code 2.1.280 — auth and request-flow audit

Date: 2026-09-22
Method: content-level diff of the extracted bundles (chunk file names are randomized per build, so
filename diffs are meaningless). For every chunk in each version I extracted the string-literal set,
matched modules across versions by literal-set similarity, then beautified (`jsbeautify -d`) and read
each module that actually changed.

  v278: `~/SiteResearch/anthropic/v2.1.278/extracted`  (1902 chunks)
  v280: `~/SiteResearch/anthropic/v2.1.280/extracted`  (1976 chunks)

Module-level result: **1023 module groups are literal-identical**; 271 changed in place; 71 were
re-bundled or rewritten. 1831 string literals exist in 2.1.280 that appear nowhere in 2.1.278.

## Headline: the wire auth contract did not move

Everything `anthropic-auth` impersonates is unchanged. Evidence, not assertion:

| surface | evidence |
|---|---|
| OAuth endpoints | the set of `/oauth/*`, `/api/oauth/*`, `/v1/*` path literals is **identical** (171 paths, zero added, zero removed) |
| OAuth scopes | scope literal set identical (`user:inference`, `user:profile`, `org:create_api_key`, …) |
| request headers | the `anthropic-*` / `x-*` header literal set is identical; the only diffs are 1–2 character minifier artifacts (`x-de`, `x-u`, …), not header names |
| billing header | the module that builds and recognizes the `x-anthropic-billing-header:` system block normalizes byte-identical between versions |
| unified rate-limit headers | `anthropic-ratelimit-unified-{status,reset,overage-status,representative-claim}` — parser module normalizes identical |
| trusted devices / attestation | the `/api/auth/trusted_devices` enrollment module normalizes byte-identical (`chunk-w2rzj6ta.js` → `chunk-frftnywc.js`); only a new *dialog* was added |
| beta registry | 36 betas in both builds; exactly one added, none removed, relative order otherwise unchanged |

So no change is required to our OAuth flow, credential store, signing, or header construction.

## What did change

### 1. One new beta: `inline-tools-2026-09-15`

The frozen beta candidate list gained exactly one entry, inserted directly after
`mid-conversation-tool-changes-2026-07-01` and before `server-side-fallback-2026-06-01`:

```
… files-api-2025-04-14, environments-2025-11-01, ccr-byoc-2025-07-29,
  mid-conversation-system-2026-04-07, per-turn-control-2026-07-01, timing-2026-09-09,
  mid-conversation-tool-changes-2026-07-01,
+ inline-tools-2026-09-15,
  server-side-fallback-2026-06-01, server-side-fallback-2026-07-01, fallback-credit-2026-06-01 …
```

It lets a mid-conversation `role:"system"` message define a tool inline
(`{type:"tool_addition", tool:{type:"tool_definition", definition:{…}}}`) instead of referencing one
already declared in `tools[]`. Gated by model capability, env `CLAUDE_CODE_INLINE_TOOLS`, and gate
`tengu_brisk_meadow`. **Not applicable to us** — neither host emits mid-conversation tool definitions.

The full 2.1.280 registry is recorded in the appendix below; our five betas
(`oauth-2025-04-20`, `interleaved-thinking-2025-05-14`, `effort-2025-11-24`,
`fast-mode-2026-02-01`, `context-1m-2025-08-07`) all still exist in the binary.

### 2. A new authenticated egress path: `/api/event_logging/v2/batch`

`POST https://api.anthropic.com/api/event_logging/v2/batch`, header `x-service-name: claude-code`,
authorized with the **same OAuth bearer** used for inference. It backs a new plugin-facing
`$.telemetry.log` / `$.telemetry.mark` API, restricted to plugins whose `origin.tier` is `builtin` or
`core` (anything else gets `"$.telemetry serves the plugins built into Claude Code alone"`).

The batch body carries `deviceId` (the config `userID`), `accountUuid`, `organizationUuid`, and —
only when `userType === "ant"` — the account email, plus a machine profile gathered by running
`uname -s/-r/-m` and probing for npm/yarn/pnpm/bun/deno/node.

It is suppressed when any of these hold (`isAnalyticsOff`): `NODE_ENV=test`, `DISABLE_TELEMETRY`,
`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, `DO_NOT_TRACK`, any third-party provider
(bedrock/vertex/foundry/anthropic_aws/anthropic_google_cloud/mantle) without
`providerManagedByHost`, gateway login, or a **custom OAuth URL**. Requires a first-party
credential — it throws `"this session has no first-party credential to authorize"` otherwise.

Relevance to us: it is a new place the subscription token is spent, and it is the first Claude Code
egress that ships account UUID + org UUID + machine fingerprint together. We do not need to
reproduce it, and we should never reproduce it.

### 3. Proactive credential-rotation detection in the retry loop

This is the one change that touches the same problem `anthropic-auth` solves. In the main retry
generator the SDK client is rebuilt when the stored token no longer matches the token the client was
constructed from:

```js
function xfr(e){ let n = rn()?.accessToken; return n !== void 0 && n !== e }        // token moved under us
…
let Et = Le !== void 0 && Boolean(a.CLAUDE_CODE_REMOTE_SESSION_ID) && xfr(Le);
if (Et) t("Credential rotated since the client was built \u2014 rebuilding before retry");
if (h === null || Et || w instanceof Ct && w.status === 401 || ORe(w) || …) { /* rebuild client */ }
```

2.1.278 had the same loop without the `Et` disjunct — it only rebuilt on a 401 or a transport fault.
This is Anthropic acknowledging the exact failure mode recorded in our own notes: Anthropic rotates
the refresh token on every refresh, so a long-lived client can hold a superseded access token and
get a confusing `429 rate_limit_error` rather than a 401.

Their fix is narrow — gated on `CLAUDE_CODE_REMOTE_SESSION_ID`, so only remote sessions get it.
**We are already ahead here and need no change:** the OpenCode fetch wrapper calls
`getAuth()` on every request, which re-reads the canonical shared store and the sidecar, and Pi's
`streamCortexKitAnthropic` reads `loadSharedAccountStore()` per request. Neither caches a token
across requests the way a built SDK client does.

### 4. Broader HTTP 407 proxy handling

`w.status === 407 && QZe()` became a helper that also unwraps a 407 nested inside an
`ERR_PROXY_TUNNEL` error chain and captures the `proxy-authenticate` header:

```js
function DRe(e){
  if (e instanceof xp){ let n = Qz(e, r => v(r) === "ERR_PROXY_TUNNEL");
    if (n && "status" in n && n.status === 407)
      return { proxyAuthenticate: (…headers…)?.get("proxy-authenticate") ?? void 0 };
    return }
  if (e instanceof Ct && e.status === 407)
    return { proxyAuthenticate: e.headers?.get("proxy-authenticate") ?? void 0 };
}
```

Relevant only to users behind an authenticating proxy; our transport surfaces the error to the host.

### 5. Environment variables

Added: `CLAUDE_CODE_INLINE_TOOLS`, `CLAUDE_CODE_RUSTLING_PIXEL` (tri-state foreign-thinking
retention, replaces the boolean `CLAUDE_CODE_LUMINOUS_WHISTLE`), `CLAUDE_CODE_PER_TURN_TIMING`
usage, `CLAUDE_CODE_AUTO_MODE_CLASSIFIER_OVERLAP`, `CLAUDE_CODE_DIR_SYNC_CHAIN`,
`CLAUDE_CODE_HOST_SCHEDULED_RUN`, `CLAUDE_CODE_MAX_EFFORT_REMINDER`,
`CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH`, `CLAUDE_CODE_PLUGIN_DIRS`,
`CLAUDE_CODE_REMOTE_TOOLS_ASK_SEATS`, `CLAUDE_CODE_REMOTE_TOOLS_JUMP_QUEUE`.
Removed: `CLAUDE_CODE_LUMINOUS_WHISTLE`.

None of them change a request we send.

### 6. Device re-enrollment is UI only

Three new gates (`tengu_device_reenroll`, `tengu_device_reenroll_prompt`,
`tengu_device_reenroll_prompt_shown`) back a new dialog: *"This computer was removed from your
devices … Register it again to let this and later cloud sessions use this computer."* The underlying
trusted-device protocol module is byte-identical to 2.1.278, and every device-binding refusal reason
(`account_mismatch`, `device_revoked`, `bind_attestation_stale`, `no_keychain`, `limit_reached`, …)
already existed in 2.1.278.

## Quota model (unchanged, recorded for reference)

The limit-scope enum Claude Code uses for reset grants — unchanged between 2.1.278 and 2.1.280:

```
five_hour, seven_day, seven_day_overage_included, seven_day_opus, seven_day_sonnet,
seven_day_cowork, seven_day_omelette, seven_day_oauth_apps
```

Our sidecar models `five_hour`, `seven_day`, and per-model scoped windows, which covers the ones a
subscription CLI account actually receives. The `cedar_ember` (limit-reset grant claim) and
`juniper_tide` (tier / tenure / billing-path metadata: `claude_pro | claude_max_5x | claude_max_20x`,
`stripe | apple | google_play`) experiments both predate 2.1.280.

## Worker report: credential and identity lifecycle

Full report: [`2026-09-22-cc-2.1.280-auth-lifecycle.md`](./2026-09-22-cc-2.1.280-auth-lifecycle.md).
Independently reached the same bottom line — nothing an impersonating OAuth client sends, stores, or
must expect changed — with these specifics.

**Verified byte-for-byte unchanged** (chunk sizes identical, fingerprint diff empty):

- OAuth config module, 4795 B both sides, diff = the version string only:
  `CLIENT_ID 9d1c250a-e61b-44d9-88ed-5944d1962f5e`,
  `TOKEN_URL https://platform.claude.com/v1/oauth/token`, the API-key/roles URLs, the manual
  redirect URL, beta `oauth-2025-04-20`, the full scope lists, and the
  `CLAUDE_CODE_CUSTOM_OAUTH_URL` three-host allow-list.
- Authorize URL: same parameters **and the same append order** —
  `code, client_id, response_type, redirect_uri, scope, code_challenge,
  code_challenge_method=S256, state`, then optional `orgUUID` / `login_hint` / `login_method`.
- Loopback callback server, 7601 B both: `listen(port ?? 0, "127.0.0.1")`, `/callback`,
  state mismatch → 400.
- Token exchange, refresh, and revoke: bodies, headers, and timeouts literal-identical; the 5-minute
  (300 000 ms) skew window; the 3-try compare-and-swap refresh-token save with `100 ms × i` backoff;
  `invalid_grant` / `account_on_hold` classification; `POST ${TOKEN_URL}/revoke`
  `{token, token_type_hint, client_id}` with a 5 s timeout.
- Credential storage: keychain naming module 2877 B both, diff empty — service
  `Claude Code${OAUTH_FILE_SUFFIX}${suffix}`, account `$USER`; `.credentials.json` still written
  mode `0600`; the `claudeAiOauth` and `oauthAccount` field sets are identical; **no migration code
  runs on upgrade**.
- API-key path, `/api/oauth/claude_cli/roles`, and the `x-api-key` vs `authorization` decision
  (32 identical call sites); `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_API_KEY` /
  `CLAUDE_CODE_OAUTH_TOKEN(_FILE_DESCRIPTOR)` / `CCR_OAUTH_TOKEN_FILE` / `apiKeyHelper` resolver
  unchanged.
- `/api/claude_cli/bootstrap` (11 585 B both, diff = build stamp), `/api/oauth/profile`,
  `/api/oauth/validate`, `/api/oauth/account/settings`: empty diffs.
- Trusted-device core module 6900 B both, empty diff, same 20 exports; device key store
  (keychain `"Claude Code-device-keys"`, `0600` file fallback) unchanged.

**Real changes, all outside the subscription-credential path:**

1. **Cowork device re-enrollment.** Registration itself is unchanged
   (`POST /api/organizations/:orgUUID/cowork/remote_devices`
   `{display_name, platform, public_key}`, `anthropic-beta: oauth-2025-04-20`, same
   `cowork_remote_device_{limit_reached,registration_revoked}` codes). New: the revoked error now
   carries `refusedPublicKey`; the client retires that key (re-read verify, 2 attempts, else
   `key_not_retired`) and re-registers with `{relearn: true}`, asking the user once through the new
   `DeviceReenrollDialog`. The three `tengu_device_reenroll*` events are the **only** additions to
   the entire auth/device/token event namespace.
2. **A third Cowork signing domain**, `anthropic.ccr.tool_host_link.v1`:
   `prefix ‖ org ‖ account ‖ session ‖ device ‖ u16be(len workId) ‖ workId ‖
   u16be(len environmentId) ‖ environmentId ‖ u64be(now)`, joining the existing
   `create_session_bind.v1` and `session_bind.v1`. Same envelope
   `{deviceUUID, kid:"creg_"+uuid, signature, issuedAt}`.
3. **Trusted-device token renewal on 403** for `GET /v1/code/sessions/{id}/events`: mint a fresh
   `X-Trusted-Device-Token`, retry once, then classify `untrusted_device`.

**Known gap, deliberately not closed.** `packages/core/src/cowork-binding.ts` implements only
`create_session_bind.v1`. Claude Code has had `session_bind.v1` since before 2.1.278 and now adds
`tool_host_link.v1`. Neither OpenCode nor Pi drives a Cowork tool-host session, so implementing two
more length-prefixed signing preimages would add unused signing surface for no current caller. The
preimage layouts are recorded above if that changes.

## Change made in response to this audit

2.1.280 adds a `safety_monitor_blocked` error kind (its predicate is hardcoded `return false` —
pre-wiring) and a `policy_blocked` classifier keyed on HTTP 400 with
`error.error.type === "policy_blocked"`. These already fell out of our `classifyRetry` as
non-retryable, because they are non-429 4xx. What was missing was a *name*: the user saw a raw 400
body. `classifyProviderBlock()` in `packages/core/src/retry-policy.ts` now recognizes
`policy_blocked`, `dlp_request_denied`, and `safety_monitor_blocked`, and both hosts report the
matching verdict instead of the raw body.
