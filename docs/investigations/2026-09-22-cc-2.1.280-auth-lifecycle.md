# Claude Code 2.1.278 → 2.1.280 — credential & identity lifecycle diff

**Scope:** OAuth login, token refresh/expiry, credential storage, logout/revoke, trusted
devices / attestation / remote-control tokens, API-key path, and bootstrap/profile/validate/
account-settings endpoints.

**Method.** Chunk file names are randomized per build, so nothing was compared by name.
Every `.js`/`.mjs` chunk in each extract was loaded in Python and indexed by content; auth
modules were located by anchor strings (`grant_type`, `code_verifier`, `trusted_devices`,
`create_api_key`, `.credentials.json`, `secret-tool`, …), beautified with
`jsbeautify -d`, then compared on a **semantic fingerprint** (string literals + property
names + object keys) instead of raw text, so pure minifier renames cancel out.

* v278 extract: `/home/cole/SiteResearch/anthropic/v2.1.278/extracted` (1904 JS chunks, 42.1 MB)
* v280 extract: `/home/cole/SiteResearch/anthropic/v2.1.280/extracted` (1978 JS chunks, 38.7 MB)
* Build stamps: `2.1.278` / `BUILD_TIME 2026-09-19T01:12:36Z` / `GIT_SHA 809c980662e3525645594dc8b74f78c38a348db1`
  → `2.1.280` / `2026-09-21T20:40:17Z` / `80abbfe7d7232280011ff01a21ae3338f4c6e372`.

## TL;DR for `anthropic-auth`

**Nothing a Claude-Code-impersonating OAuth client sends, stores, or must expect has changed.**
Authorize URL, PKCE, client id, redirect URIs, scopes, token exchange, refresh, revoke,
credential file shape/permissions, keychain naming, API-key minting and the bootstrap/profile/
validate/roles endpoints are all literal-identical between 2.1.278 and 2.1.280.

The three real deltas are all **outside the subscription-credential path**:

1. **Cowork/Remote-Control device re-enrollment** — new client flow when a device
   registration was revoked server-side.
2. **Trusted-device token renewal on 403** for the remote-session event stream.
3. **`safety_monitor_blocked`** — a new *permanent* API error class wired into the request
   loop, currently inert (its predicate returns `false`).

## 2. Token refresh + expiry — NO CHANGE

Refresh call, identical in both:

```js
POST ${TOKEN_URL}
{ grant_type:"refresh_token", refresh_token, client_id, scope:<scopes.join(" ")> [, expires_in] }
headers { "Content-Type":"application/json" }, timeout 30000, signal
status !== 200 → Error(`Token refresh failed: ${statusText}`)
```

Unchanged surrounding logic (same literals, same order):

* Early-refresh/clock-skew window: `expiresAt !== null && now + 300000 >= expiresAt` (5 min).
* `refresh_token_expires_in` handling with the same defaults: `86400000` (profile TTL) and
  `2592000000` (30 d fallback refresh-token lifetime).
* Cross-process refresh lock + **compare-and-swap** save: up to 3 attempts, `await sleep(100*i)`
  backoff, CAS predicate `stored.claudeAiOauth?.refreshToken === postedRefreshToken || ""`,
  outcomes `saved` / `save_failed` / `adopted_sibling`, events
  `tengu_oauth_tokens_saved`, `tengu_oauth_tokens_save_failed`, `tengu_oauth_tokens_save_exception`,
  `tengu_oauth_refresh_save_adopted_newer_write`,
  `tengu_oauth_token_refresh_lock_compromised_post_post`,
  `tengu_oauth_refresh_compromised_cas_{saved,adopted_sibling}`.
* `invalid_grant` classification: axios error with status 400/401/403 whose body parses to an
  OAuth error; separate `account_on_hold` branch; telemetry
  `oauth_refresh_invalid_grant` / `oauth_refresh_account_on_hold` / `oauth_refresh_request_failed`;
  invalid-scope single retry (`invalid_scope_retried`) unchanged.
* Rotation result shape unchanged: `{accessToken, refreshToken, expiresAt, refreshTokenExpiresAt,
  scopes, subscriptionType, rateLimitTier, clientId, profile, tokenAccount{uuid,emailAddress,organizationUuid}}`.

The complete `tengu_*` telemetry set matching `oauth|auth|device|trust|login|logout|credential|token|api_key|account`
gained exactly three names (all device re-enroll, §5) and lost one unrelated one
(`tengu_plugin_autoupdate_allow_credential_helper`).

second, plugin-API copy with its own hardcoded endpoint.

## 5. Trusted devices / attestation / remote control — **REAL CHANGES**

### 5a. Device re-enrollment after server-side revocation (new)

Core trusted-device module is unchanged: v278 `chunk-w2rzj6ta.js` ↔ v280 `chunk-frftnywc.js`
are both 6900 bytes raw with an empty string/prop/key diff, and the public barrel
(`clearTrustedDeviceToken`, `enrollTrustedDevice`, `enrollTrustedDeviceIfNeeded`,
`ensureTrustedDeviceTokenForBind`, `getAttestationFilterPolicy`, `getTrustedDeviceToken`,
`isTrustedDeviceActiveForOrg`, `preflightTrustedDeviceBlocking`,
`readStoredTrustedDeviceToken`, `recoverFromUntrustedDevice`, `withUntrustedDeviceRecovery`, …)
exports the **same 20 names** in both.

What changed is the *device-bind* layer (v278 `chunk-tsq1ysdf.js` 4294 B → v280
`chunk-hd0hc2nm.js` 5880 B) and the *device-registry* layer
(v278 `chunk-q2vfrb8g.js` 13645 B → v280 `chunk-pfc72yjg.js` 14177 B).

The registration request is **unchanged**:

```js
POST /api/organizations/:orgUUID/cowork/remote_devices
{ display_name, platform:"linux", public_key: <SPKI b64> }
headers { "anthropic-beta": "oauth-2025-04-20" }, auth:"teleport-org", timeout 10000
error codes: cowork_remote_device_limit_reached, cowork_remote_device_registration_revoked
```

New in 2.1.280:

* The "revoked" error now carries `refusedPublicKey` (the SPKI the server rejected).
* New re-enroll entry point: drop the refused key from the device key store (verified by
  re-reading, 2 attempts, else `key_not_retired` / "the removed device's key could not be
  retired"), then re-register with `{ relearn: true }`.
* `$Ao`/device-bind asks the host first, exactly once per bind, through a new
  `confirmReenroll` callback, and records
  `tengu_device_reenroll { confirmed, prompt_failed }`.
* New interactive dialog `DeviceReenrollDialog` (v280 `chunk-m9w3nv38.js`):
  title *"This computer was removed from your devices"*, options
  `Yes, register this computer again` / `Not now` (default `not_now`), emitting
  `tengu_device_reenroll_prompt_shown` and
  `tengu_device_reenroll_prompt { choice: register|not_now|cancelled|unmounted }`.

Device **key storage** is unchanged: keychain service `"Claude Code-device-keys"`,
`security find-generic-password -a $USER -w -s …` with exit 44 = absent and {37,50} = no login
keychain, hex-encoded `add-generic-password -U -X` write (stdin form under 4032 bytes),
file fallback written 0600 with corrupt-document quarantine
(`device_key_store/corrupt_quarantined`), and the `.device-keys` proper-lockfile.

### 5b. New Cowork signing domain `anthropic.ccr.tool_host_link.v1` (new)

2.1.278 had two Ed25519/P-256 signing preimages:

* `anthropic.ccr.create_session_bind.v1` — `prefix ‖ orgUuid ‖ accountUuid ‖ deviceUuid ‖ u64be(now)`
* `anthropic.ccr.session_bind.v1` — `prefix ‖ org ‖ account ‖ session ‖ expectedCurrentDevice ‖ newDevice ‖ u64be(now)`

2.1.280 adds a third:

* `anthropic.ccr.tool_host_link.v1` —
  `prefix ‖ org ‖ account ‖ session ‖ device ‖ u16be(len workId) ‖ workId ‖ u16be(len environmentId) ‖ environmentId ‖ u64be(now)`,
  ids constrained to 1..65535 bytes.

All three emit the same envelope `{ deviceUUID, kid:"creg_"+deviceUUID, signature:<b64>, issuedAt:<ISO> }`.

### 5c. Trusted-device token renewal on 403 (new)

Remote-session event fetch (v278 `chunk-jxm1s6qb.js` ↔ v280 `chunk-82893emm.js`) gained a
`recoverDeviceProof` option. When `GET ${BASE_API_URL}/v1/code/sessions/{id}/events` returns
**403** and recovery is armed, the client mints a fresh trusted-device token and retries with
`X-Trusted-Device-Token: <new>`; if the retry is still 403 and the body classifies as
`untrusted_device`, it throws "the service does not accept a trusted-device token from this
computer". Same chunk also gained plural `user_message_uuids` frames and
`remote_tools_reannounce`. The `X-Trusted-Device-Token` header name, `CLAUDE_TRUSTED_DEVICE_TOKEN`,
`local_pairing`, `CLAUDE_CODE_SESSION_ACCESS_TOKEN`, `SESSION_INGRESS_URL`,
`CLAUDE_SESSION_INGRESS_TOKEN_FILE`, `CLAUDE_CODE_WEBSOCKET_AUTH_FILE_DESCRIPTOR`,
`CCR_OAUTH_TOKEN_FILE`, `CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR` and the
`/v2/session_ingress/*`, `/v2/ccr-sessions/`, `/v1/code/` path families are all present and
unchanged in both builds.

## 8. Adjacent finding: new permanent API error class (inert)

v280 `chunk-nm3tx8s2.js` adds, next to the existing `dlp_request_denied` and
`claude_code_version_too_old` classifiers:

```js
function ufo(e){ return e.status===400 && e.error?.error?.type==="policy_blocked" }  // new use of policy_blocked
var fK = "safety_monitor_blocked";
function Rrt(e){ return false }                                                      // predicate disabled
```

`Rrt` is wired into the request loop as a **non-retryable** terminal error
(`api_request_safety_monitor_blocked`, alongside `api_request_dlp_denied`), and
`safety_monitor_blocked` was added to the SDK `api_error` union. Because the predicate is
hardcoded `false` in 2.1.280, no client currently classifies anything this way — treat it as
pre-wiring for a future server-side rejection kind. `safety_monitor_blocked` appears in 4
chunks in v280 and **0** in v278.

## Action for `anthropic-auth`

**None required.** No change to request construction, credential storage, refresh behaviour,
or error expectations. Optional, low priority:

* If the relay/quota layer ever classifies provider errors by `error.error.type`, note that
  `policy_blocked` (400) and `safety_monitor_blocked` are now permanent, non-retryable classes
  upstream — worth adding to the permanent-error set before Anthropic enables the latter.
* Nothing in the Cowork device-bind / trusted-device changes applies, because `anthropic-auth`
  does not enroll devices or use Remote Control.
